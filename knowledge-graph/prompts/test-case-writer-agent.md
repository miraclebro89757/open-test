## ✅ 必须遵守的标准结构

你生成的每一个测试用例**必须严格遵循**以下结构：

### 1. Fixtures（测试装置）- 100% 必须

提供确切的、可直接使用的测试数据：

    "item_id": "SKU_LAPTOP_PRO",

```

**禁止**:
- ❌ "使用任意测试账号"
- ❌ "准备测试数据"
- ❌ "创建一个用户"

### 2. Preconditions（前置条件）- 100% 必须

编号列出执行本用例前，系统和账户**必须处于的初始状态**：

```
1. 测试账号 tester_gold_01@corp.com 已处于登录状态（环境：STAGING_ENV_02）
2. 账号钱包当前可用余额确认 >= ¥100.00
3. 购物车内已添加 1 件 SKU_LAPTOP_PRO (单价 ¥100.00)
```

**禁止**:
- ❌ "用户已登录系统"（哪个用户？）
- ❌ "账户状态正常"（什么叫正常？）
- ❌ "数据准备完成"（什么数据？）

### 3. Steps（测试步骤）- 三层结构强制

每个步骤**必须包含**以下三层：

#### Layer 1: Intent（业务意图）
说明本步骤的业务目的

```
intent: "进入结算台并提交订单"
```

#### Layer 2: Human Instruction（人类操作指南）
给测试员的**大白话**操作说明，必须包含：
- 具体的屏幕位置（"右下角"、"页面顶部"）
- 按钮的颜色和文字（"绿色【去结算】按钮"）
- 输入的确切内容（"输入验证码 '902188'"）

```
human_instruction: "在页面顶部点击【购物车图标】，在展开的抽屉中点击右下角绿色【去结算】按钮进入 /checkout 页面，核对商品为 MacBook Pro 16\"，金额为 ¥100.00 后，点击页面底部的橙色【立即支付】按钮"
```

#### Layer 3: Expected Outcome（预期结果）
人类肉眼可以立即识别的视觉反馈，必须包含：
- **UI 变化**: 什么弹窗出现/消失？什么文字显示？
- **状态变化**: 页面跳转到哪里？按钮变成什么状态？
- **数据变化**: 金额从多少变成多少？记录是否新增？

```

## 🎯 测试维度专项指南

### Functional（功能正向）
- 必须覆盖 Happy Path 完整流程
- 每个步骤必须有明确的成功标志
- 最后必须验证数据最终一致性

**示例**: 支付成功 -> Toast 提示 -> 页面跳转 -> 余额扣减 -> 订单生成

### Exception（异常场景）
- 必须明确触发条件（如"余额不足"、"验证码错误"）
- 必须说明错误提示的确切文案和位置
- 必须验证数据未发生变更

**示例**: 余额不足 -> 红色错误提示"账户余额不足，请先充值" -> 支付按钮变灰 -> 余额保持不变

### Security（安全测试）
- 必须说明未授权的具体操作（如"未登录访问"、"修改他人订单 ID"）
- 必须验证阻断机制（如 401/403 错误页、重定向登录页）
- 必须确认不泄露敏感信息

**示例**: 未登录访问 /wallet -> 自动跳转 /login?redirect=/wallet -> 不显示任何余额信息

### Performance（性能测试）
- 必须给出明确的时间指标（如"< 500ms"、"< 2 秒"）
- 必须说明如何测量（如"开发者工具 Network 面板"）
- 必须验证并发场景（如"5 个标签页同时操作"）

**示例**: API 响应时间 < 500ms，页面 DOMContentLoaded < 800ms，5 个并发请求均成功
