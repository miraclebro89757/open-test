测试 Agent 最值得做、也最能体现专业价值的能力之一：不是每次从新需求生成一套测试用例，而是理解产品发生了什么变化，并持续维护一套可信的测试资产。

我建议把它设计成 OpenTest 的一个独立核心能力：

# Test Evolution：需求与测试资产的持续演进

它解决的不是简单的文档 diff，而是三个相互关联的问题：

1. 版本迁移： 老需求中的哪些内容被保留、修改、删除或替代？
2. 测试资产迁移： 老版本的用例哪些继续有效，哪些需要修改，哪些应该废弃，哪些场景需要新增？
3. 回归资产建设： 哪些核心场景值得长期保留，并逐步转化成稳定、可维护的自动化回归集？

这里最关键的设计原则是：

需求文档的变化，不等于测试用例的变化；测试用例的变化，也不等于自动化脚本的变化。

三者有关联，但不能直接一对一地同步删除或覆盖。否则，新版本删掉一个需求描述，Agent 就可能错误地删除仍然重要的兼容性测试；或者需求重构后，原本有效的测试用例因为措辞改变而被重复生成。

# 一、先建立正确的数据模型：不要让新需求覆盖旧需求

假设你的项目经历了下面的变化：

- V1：用户登录、商品查询、创建订单、取消订单。
- V2：登录方式重构，商品查询逻辑调整，创建订单流程重写，取消订单功能被移除，新增退款功能。

你原本已经有一套 V1 需求、测试点、测试用例和部分自动化脚本。现在不能简单地把 V2 文档喂给 Agent，再生成一套全新的用例。

因为那样会丢失历史测试资产，也无法解释哪些测试为什么被删除、哪些测试为什么需要修改。

## 1.1 建立四层对象

需求版本 Requirement Version

V1 需求 · V2 需求 · 原文位置 · 验收标准

需求演进关系 Requirement Evolution

保留 · 修改 · 拆分 · 合并 · 新增 · 删除 · 待确认

测试资产 Test Assets

测试点 · 用例 · 历史结果 · 自动化脚本

回归策略 Regression Policy

核心场景 · 自动化候选 · 必跑集合 · 风险覆盖

这四层需要独立维护。

特别是 `Requirement Evolution`：它不是一份简单的文档差异报告，而是一个显式记录新旧需求之间语义关系的对象。

## 1.2 每条需求都应该有稳定 ID

例如：

| 需求 ID         | V1 状态 | V2 状态    | 演进关系      |
| ------------- | ----- | -------- | --------- |
| REQ-LOGIN-01  | 手机号登录 | 手机号登录    | 保留，验收标准修改 |
| REQ-ORDER-01  | 创建订单  | 新的创建订单流程 | 修改或重构     |
| REQ-CANCEL-01 | 取消订单  | 无对应功能    | 待确认是否废弃   |
| REQ-REFUND-01 | 不存在   | 退款申请     | 新增        |

这里有一个重要细节：需求 ID 不应该仅仅根据标题或文本自动生成。

可以使用永久 ID 标识一个需求概念，同时用独立的版本 ID 标识每次修改后的内容。如果一个旧需求被拆成多个新需求，或者多个旧需求被合并，应该记录明确的映射关系，而不是强行保留一对一对应。

如果新旧需求之间无法确定关系，就标记为待确认，不要让模型猜一个看似合理的映射后直接执行。

# 二、核心机制：先做需求差异分析，再做测试资产迁移

我建议将整个过程设计成一个独立的 `Evolution Session`，即一次可保存、可审核、可恢复的版本演进任务。

## 2.1 完整工作流

### 01

导入新版本

冻结 V1 基线，导入 V2，记录版本和文件来源

### 02

需求语义对齐

结合 ID、内容、验收标准和上下文，匹配新旧需求

### 03

生成变更集

识别新增、修改、删除、拆分、合并和不确定项

### 04

评估测试影响

逐条关联旧测试点、用例、脚本和历史执行记录

### 05

生成迁移方案

保留、修改、补充、废弃、人工确认

### 06

审核与应用

审核变更差异，批准后创建新版本测试资产

### 07

识别核心回归集

依据风险、业务重要性和覆盖关系选出自动化候选

### 08

验证与发布

运行必要测试，更新回归策略和质量报告

这里的核心是将过程拆成两次判断：

- 第一遍判断：需求究竟发生了什么变化？
- 第二遍判断：这些变化对已有测试资产意味着什么？

不能直接从文档差异跳到用例生成。

## 2.2 需求差异不应该只有新增、删除、修改三种

真实项目里的需求重构往往更复杂。

| 变化类型    | 示例               | Agent 的处理策略             |
| ------- | ---------------- | ----------------------- |
| 新增      | 增加退款功能           | 新建需求、测试点与用例候选           |
| 修改      | 登录增加失败锁定规则       | 找到相关测试点，补充边界和异常用例       |
| 删除      | 不再支持旧版取消订单       | 检查关联用例及兼容性要求，提出废弃建议     |
| 拆分      | 一个订单需求拆成创建、支付、关闭 | 将旧需求和测试资产映射到多个新需求       |
| 合并      | 两个重复的商品查询需求合并    | 合并映射关系，检查重复用例           |
| 重构但行为不变 | 内部模块替换，用户行为保持一致  | 优先复用原有行为测试，评估是否需要增加集成测试 |
| 语义不确定   | 新文档没有提及旧功能       | 标记待确认，不能直接当作功能删除        |

最后一种特别重要。

新文档没有写某个功能，不等于产品已经决定删除这个功能。

如果 Agent 无法判断，就应提出问题：“旧版支持取消订单，新版文档未提及。请确认该功能是删除、迁移，还是需求文档遗漏。”

这比模型自行推断安全得多。

# 三、测试用例怎么跟着需求一起迭代？

这里是整个设计最重要的部分。

我建议给每条测试用例建立一个独立的生命周期，并且把“用例是否仍然有效”和“用例是否适合自动化”拆成两个维度。

## 3.1 不要只用一个状态字段

假设旧版有以下测试用例：

| 用例     | 原始场景    | V2 初步判断          |
| ------ | ------- | ---------------- |
| TC-001 | 正确手机号登录 | 保留并重新验证          |
| TC-002 | 错误密码登录  | 修改，适配新的错误提示和锁定规则 |
| TC-003 | 创建订单成功  | 保留业务意图，更新执行步骤    |
| TC-004 | 旧版取消订单  | 待确认是否废弃          |
| TC-005 | 订单重复提交  | 继续保留，并评估是否属于核心回归 |
| TC-006 | 退款申请成功  | 新增               |

不要把所有状态都塞进一个 `status` 字段。建议至少分成三个维度。

A. 生命周期 `lifecycle`

active

needs_update

deprecated

pending_review

描述这条用例在当前产品版本中是否有效。

B. 验证状态 `verification`

not_run

passed

failed

blocked

stale

描述当前版本的行为是否经过实际验证，以及结果如何。

C. 自动化状态 `automation`

manual

candidate

automated

unstable

maintenance_needed

描述这条用例是否适合自动化、是否已有脚本，以及脚本是否需要维护。

这样一条用例可以是：

- `active + stale + automated`：用例仍然有效，但新版尚未重新验证，已有自动化脚本需要重新运行。
- `active + passed + manual`：用例有效且已经通过验证，但暂时由人工执行。
- `needs_update + not_run + maintenance_needed`：用例需要更新，尚未验证，关联脚本也需要维护。
- `deprecated + passed + automated`：旧版本曾经通过且有自动化脚本，但该用例已被当前版本废弃。历史结果仍然保留。

这能防止一个常见错误：Agent 看到脚本跑通了，就误以为它覆盖的需求仍然有效；或者看到需求已删除，就把旧版本的执行历史一起删除。

## 3.2 为测试用例增加“行为意图”，而不只是步骤

传统测试用例经常是这样的：

```
1. 打开登录页面
2. 输入手机号
3. 输入密码
4. 点击登录
5. 检查页面跳转
```

这种描述太依赖当前 UI。页面一重构，整个用例看起来就需要重写。

建议为用例同时保存两层内容：

行为意图层

```
id: TC-LOGIN-001
intent: valid_user_can_login
requirement_ids:
  - REQ-LOGIN-01
preconditions:
  - account_is_active
action:
  - authenticate_with_valid_credentials
expected:
  - authentication_succeeds
  - user_session_is_created
risk: high
```

执行实现层

```
implementation:
  type: playwright
  file: tests/auth/login.spec.ts
  status: maintenance_needed
  last_verified_version: v1
```

上面的 YAML 是概念示例，不是某个现成标准要求的格式。

这样，V2 即使重构了登录页面、调整了组件层级，Agent 也可以先判断业务行为是否变化，再决定需要修改哪些 UI 操作和定位器。

需要注意，行为意图本身也不是永远不变的。比如新版登录增加了多因素认证，那么旧用例的前置条件和预期行为可能也需要演进。

## 3.3 用“变更影响图”找出真正受影响的用例

我建议建立以下关联：

需求变更 REQ-LOGIN-01

关联测试点 TP-LOGIN-03

登录失败与账号锁定

TC-LOGIN-006

需要更新

锁定阈值发生变化

TC-LOGIN-007

待复核

错误提示可能变化

影响评估

关联脚本 · 核心回归集 · 历史结果 · 执行建议

Agent 应该优先沿着显式的需求—测试点—用例—脚本关系查找影响范围，再使用语义相似度发现可能漏掉的关联。

不要反过来只靠向量搜索猜测哪些用例相关。语义搜索适合补充发现，明确的 ID 和关系才是可信的追溯基础。

## 3.4 用例迁移必须输出差异，而不是直接覆盖

对每条受影响的旧用例，Agent 应当生成一份迁移提案：

- 原用例是什么。
- 新版需求改变了什么。
- 为什么这条用例需要修改或保留。
- 建议修改哪些前置条件、步骤、预期结果。
- 哪些历史执行结果仍然有效，哪些结论需要重新验证。
- 关联脚本需要怎样调整。
- 当前有哪些信息仍然不确定。

然后通过批量审核界面执行：

- 接受迁移。
- 手动编辑。
- 保留旧版并建立新版。
- 标记为废弃。
- 暂缓处理。

这比“让 AI 自动同步新旧测试用例”更可靠，也更容易在团队中建立信任。

# 四、核心回归场景怎么选？不能只挑高优先级用例

你提到的另一个目标非常关键：新版本需要一份核心重要场景清单，并且优先将它们自动化。

这里我建议把回归策略独立建模，而不是简单地给用例打上 `P0` 就自动转成脚本。

因为业务重要性高，不一定意味着自动化收益高；变化频繁，也不一定意味着应该立刻自动化。

例如：

- 登录成功：业务重要，稳定性高，通常适合自动化。
- 订单金额计算：业务风险高，适合自动化，但必须有可靠的测试数据和独立的结果校验。
- 视觉细节检查：可能很重要，但不一定适合用传统 DOM 自动化覆盖全部内容。
- 每周变化一次的实验性页面：可能暂时不值得投入高维护成本的自动化脚本。

## 4.1 为每条场景建立回归评估档案

建议综合评估以下因素：

| 维度     | 需要回答的问题                 |
| ------ | ----------------------- |
| 业务重要性  | 失败会影响多少用户、收入或关键业务？      |
| 失败风险   | 是否涉及资金、数据完整性、权限或安全？     |
| 变更影响   | 新版本是否直接修改了这条路径？         |
| 使用频率   | 这是高频业务流程还是极少发生的操作？      |
| 历史缺陷   | 这条路径过去是否经常出现回归问题？       |
| 覆盖价值   | 运行这条用例能发现哪些其他用例无法发现的问题？ |
| 自动化可行性 | 是否可以稳定准备数据、执行步骤并验证结果？   |
| 维护成本   | 脚本是否容易受 UI、环境或外部服务变化影响？ |

不要急着把这些维度压缩成一个分数。第一版先保留结构化的风险说明与推荐理由，之后有真实项目数据，再校准评分和优先级。

## 4.2 将回归场景分成三个层次

### Tier 1 · Smoke Regression

每次构建优先

最短时间验证系统是否具备基本可用性。

- 登录与身份验证。
- 核心页面或 API 可用。
- 创建一笔最基本的订单。
- 关键业务状态正确。

### Tier 2 · Core Regression

发布前执行

覆盖核心业务链路、主要异常和关键边界。

- 订单创建、支付、状态变更。
- 重复提交和幂等性。
- 权限与数据隔离。
- 关键失败路径和恢复流程。

### Tier 3 · Extended Regression

按需执行

覆盖低频场景、复杂组合、兼容性及更大范围的回归。

- 多种用户状态和复杂业务组合。
- 长流程、跨模块流程。
- 浏览器兼容性和视觉检查。
- 特定历史缺陷的防复发场景。

这些层级是执行策略，不是用例生命周期状态。一个用例可以同时属于核心回归集，并在特定代码变更时被优先触发；某些低频但高风险的场景也可能需要进入发布前必跑集合。

## 4.3 自动化优先级应考虑收益和可维护性

可以给每个候选场景生成一个自动化建议：

- 优先自动化： 风险高、行为稳定、结果容易断言、运行成本合理。
- 适合后续自动化： 业务重要，但依赖、数据准备或环境稳定性尚未解决。
- 保留人工测试： 需要探索性判断，或者自动化投入暂时高于收益。
- 需要进一步分析： 需求不清楚、验收标准不明确，或者没有可靠的验证 oracle。

Agent 应该解释推荐理由，并明确依赖条件，而不是仅仅输出一个排名。

例如：

> 推荐将“订单重复提交时不会生成重复订单”纳入核心自动化回归。原因是该场景涉及数据完整性和资金风险，且可以通过订单数量、订单状态和业务唯一标识进行断言。前提是测试环境支持可控的订单数据，并且能够稳定清理测试数据。

这才是一份能真正交给自动化工程师执行的建议。

# 五、把它做成 OpenTest 的一个真正好用的功能

我建议在项目中增加一个独立入口：版本演进（Evolution）。

用户不需要先研究复杂的需求图谱，也不需要自己写提示词告诉 Agent 如何对比。系统应该引导用户完成一轮可审核的测试资产迁移。

## 5.2 哪些事情可以自动做，哪些不能？

| 操作                 | 推荐策略              |
| ------------------ | ----------------- |
| 解析需求文件和提取章节        | 自动                |
| 基于 ID、内容和上下文匹配新旧需求 | 自动提出匹配建议          |
| 生成新增测试点和用例草稿       | 自动生成，保存为候选        |
| 判断旧需求是否彻底废弃        | 默认需要确认            |
| 覆盖或删除已有测试用例        | 需要审核，保留历史版本       |
| 推荐核心回归场景           | 自动分析、说明理由、人工审核    |
| 修改自动化脚本            | 生成可审查的差异          |
| 运行测试和采集证据          | 根据权限与执行策略自动运行     |
| 发布最终测试结论           | 基于真实结果生成，并标注未解决风险 |

最重要的是：自动化程度应该随着证据和规则的确定性提高，而不是随着模型的自信程度提高。

# 六、底层怎么实现：一个可落地的 Test Evolution Engine

我不建议将版本演进实现成一个很长的 Agent Prompt。更合适的方式是将其实现为一个确定性流程与 AI 分析相结合的引擎。

## 6.1 四个核心模块

1\. Requirement Matcher

匹配新旧需求，综合稳定 ID、原文、验收标准和上下文，输出候选映射与置信依据。

2\. Impact Analyzer

沿着需求、测试点、用例、脚本和历史执行记录追踪影响范围，补充发现可能漏掉的语义关联。

3\. Migration Planner

为每个受影响的测试资产生成迁移提案，明确操作类型、变更理由、差异和待确认事项。

4\. Regression Planner

根据业务风险、变更影响、历史缺陷、覆盖价值和自动化可行性，推荐核心回归集与执行计划。

这四个模块不必是四个独立 Agent。第一版可以由一个 pi-agent 负责调用工具和组织任务，而将匹配规则、关系查询、版本管理和权限检查实现为可测试的普通代码。

这样能减少不必要的模型调用，也让关键行为更容易验证。

## 6.2 为每次演进保存一份 Migration Plan

下面是一份概念性的结构示例：

```
evolution_id: EVO-2026-001
baseline_version: v1
target_version: v2
status: review_required

requirement_changes:
  - source_id: REQ-LOGIN-01
    target_id: REQ-LOGIN-01
    change_type: modified
    confidence: high
    rationale: "登录失败规则发生变化"

test_asset_actions:
  - asset_id: TC-LOGIN-006
    action: update
    reasons:
      - "锁定阈值变化"
    requires_review: true

  - asset_id: TC-CANCEL-001
    action: pending_review
    reasons:
      - "新版本未找到对应需求"
    requires_review: true

regression_candidates:
  - test_case_id: TC-ORDER-005
    tier: core_regression
    automation_recommendation: prioritize
    rationale: "覆盖订单重复提交和数据完整性"
```

这里的 `confidence` 只是匹配或判断的依据之一，不应单独决定是否自动删除用例。

应用 Migration Plan 时，应检查基线版本是否仍然一致，避免有人在审核期间修改了同一条用例，导致旧提案覆盖新修改。对于整批应用，建议使用事务或可恢复的批处理，并保留完整的审计记录。

## 6.3 回归集不是一次性生成的，而是持续维护的

每次产品迭代后，Regression Planner 都应该回答：

- 哪些核心场景依然有效？
- 哪些场景因为需求变化需要修改？
- 哪些新增场景应加入核心回归？
- 哪些历史缺陷值得增加防复发测试？
- 哪些自动化脚本已经失效？
- 哪些场景值得从人工测试迁移到自动化？

因此，核心回归集应当是一个长期维护的集合，有自己的版本、审核记录和执行策略，而不是每次从需求文档重新生成一份列表。

# 七、第一版怎么验收？

我建议先拿一个真实的 V1 → V2 重构项目做端到端验证，不要一开始就支持所有需求格式和所有测试框架。

第一版至少应该通过以下场景：

- 能同时保存旧需求基线与新需求版本。
- 能区分新增、修改、删除、拆分、合并和待确认项。
- 能将新旧需求变化关联到已有测试点和测试用例。
- 能生成逐条可审核的用例迁移方案。
- 不会因为新版文档缺少某个需求，就自动删除相关用例。
- 保留旧版本的执行记录和脚本历史。
- 能推荐核心回归场景，并解释业务风险与自动化收益。
- 能生成新版回归集，并追踪每个场景的验证状态。
- 应用变更后可以查询完整的版本差异和审核记录。
- 当需求或用例在审核期间被其他操作修改时，能检测冲突并要求重新确认。

如果只能优先开发一项，我会先做“版本演进 + 测试资产迁移”，而不是先做自动化脚本生成。

原因很简单：脚本生成解决的是一部分执行效率问题；版本演进解决的是测试资产能否随着产品长期积累的问题。

当 OpenTest 能够理解旧版本有哪些测试资产、为什么保留它们、哪些因新版本而改变，以及哪些核心场景必须持续验证时，它才真正拥有了贯穿多个版本的 QA 能力。
