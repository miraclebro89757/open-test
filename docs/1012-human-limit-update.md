# OpenTest 开发规格：统一审批中心与 QA Agent 自主工作流

**项目：** OpenTest  
**核心目标：** 将逐阶段人工确认升级为基于风险的集中审批，让 Agent 在授权范围内连续完成 QA 任务，仅在关键决策、异常和高风险操作处请求人工介入。

**开发方式：** 基于现有 `miraclebro89757/open-test` 仓库迭代开发，先分析现有架构，再以最小改动接入。不要另建一套与现有 Pi Web、Agent Runtime、QA 资产管理系统割裂的实现。

---

## 1. 背景与要解决的问题

目前 OpenTest 已有 QA 工作台和流程展示，包含：

1. 需求分析
2. 测试点设计
3. 测试用例生成
4. 录制
5. 执行
6. 缺陷
7. 报告

当前交互存在以下问题：

- Agent 每完成一个阶段，都可能要求用户确认后才继续。
- 一份需求文档拆分成多个模块时，确认次数会快速增加。
- 用户需要在聊天区、流程面板之间来回切换，难以集中处理问题。
- 用户不容易区分哪些事项必须审核、哪些只是进度通知。
- Agent 的任务执行状态、用户审批状态、QA 资产状态容易混在一起。
- 需求版本发生变化时，旧测试点、测试用例和自动化脚本需要进行有依据的迁移，不能简单覆盖。

### 产品目标

构建一个统一的 **Approval Center（审批中心）**，参考 Codex 类 Agent 产品的待审批任务清单交互思路，但围绕 QA 工作进行设计。

核心原则：

> Agent 自主推进常规工作，系统集中呈现待决策事项，用户处理例外与关键决策，Agent 根据审核结果继续执行。

这不是单纯增加一个审批列表，而是调整整个 Agent 工作流的控制机制。

## 2. 产品设计原则

### 2.1 批量处理，避免逐步确认

Agent 完成一个阶段后，默认自动进入下一个满足前置条件的阶段，不再一律询问“是否继续”。

### 2.2 异常触发人工介入

遇到需求歧义、证据不足、核心用例可能失效、执行失败、危险操作等情况，才创建待审核事项。

### 2.3 局部阻塞，不阻塞整个任务

一个模块存在问题，不应导致其他互不依赖的模块停止工作。

例如，8 个需求模块中只有 1 个模块缺少业务规则，Agent 应继续处理另外 7 个模块，并将问题模块标记为待决策。

### 2.4 审批必须有证据

每个审批事项至少提供：

- 为什么需要人工判断。
- 相关需求、测试点或测试用例。
- 当前内容与建议内容的差异。
- Agent 的建议及其依据。
- 影响范围。
- 批准、拒绝、编辑、暂缓等可执行操作。

不能只显示“Agent 需要确认”。

### 2.5 审批和执行分离

审批通过不等于任务已执行成功。

例如，用户批准修改某个测试用例后，系统还需要执行修改、验证保存结果、更新任务状态。执行失败必须显示失败原因，不能因为审批通过就标记完成。

### 2.6 重要变更可追溯、可恢复

审批结果、变更前后内容、操作人、时间、执行结果必须可追溯。已保存的版本基线不能被原地覆盖。

## 3. 信息架构与 UI 设计

保留现有 Pi Web 的三栏工作区：

- 左侧：文件、项目文件、QA 资产导航。
- 中间：Agent 对话与执行事件。
- 右侧：QA 工作台、任务状态、资产与审批。

不要重做整个 Web Shell。优先复用现有路由、组件、会话管理和主题系统。

### 3.1 右侧工作台导航

在现有 QA 工作台中新增一级入口：

- 总览
- 需求知识
- 版本演进
- 测试点
- 用例
- 自动化脚本
- 录制
- 执行
- 自愈
- 缺陷
- 报告
- **待审核**

“待审核”是统一入口，而不是只服务于需求阶段。

建议显示待处理数量，例如：

`待审核 6`

其中高风险事项可以显示独立提示，但不要把所有进度通知都当成待审核事项。

### 3.2 审批中心页面

页面建议分为三个区域：

**A. 筛选区**

支持按以下条件筛选：

- 当前项目。
- 当前任务 / Evolution Session。
- 风险等级。
- 所属 QA 模块。
- 审批状态。
- 创建时间。
- 是否阻塞后续任务。

**B. 待审核列表**

每个列表项展示：

- 标题。
- 所属模块。
- 风险等级。
- 简短原因。
- 关联资产数量。
- 是否阻塞任务。
- 创建时间。
- 建议操作。
- 审批状态。

示例：

| 待审核事项 | 风险 | 影响 | 建议 |
|---|---|---|---|
| 需求 REQ-LOGIN-01 疑似删除 | 高 | 3 条用例、1 个脚本 | 人工确认 |
| 8 条用例标题规范化 | 低 | 8 条用例 | 批量接受 |
| 2 个测试点存在重复 | 中 | 4 条用例 | 查看差异 |
| 核心回归用例可能失效 | 高 | 回归基线 | 人工确认 |

以上为示例数据。

**C. 详情面板**

点击事项后，在侧边详情或主内容区域展示：

- 问题描述。
- 原始需求或资产内容。
- Agent 建议。
- 修改前后 Diff。
- 关联关系与影响范围。
- 证据来源。
- 审批操作。

避免每次审核都跳转到聊天区。聊天记录可以作为补充证据，但不能成为审批信息的唯一载体。

### 3.3 总览页面调整

保留现有流程进度，但区分三类状态：

- 正在执行。
- 等待人工决策。
- 已完成 / 失败。

示例：

需求分析 5/5 已完成  
测试点 20/20 已生成  
用例 49/49 已生成  
执行 1 个任务等待审核，其他模块继续处理  
报告等待执行结果

流程卡片负责展示进度；待审核中心负责呈现决策。二者共享同一份任务数据。

### 3.4 聊天区调整

聊天区继续保留，但调整其职责：

- Agent 解释工作、报告进度、回答问题。
- 关键审批事项生成结构化审批卡片。
- 用户可以从卡片打开审批详情。
- 审批结果以事件形式回写到聊天区。
- 普通进度消息不要求用户点击确认。

例如：

“已完成 8 个模块的测试点和用例生成。发现 2 个高风险问题，另有 4 个低风险优化建议。其余模块已完成，无需额外操作。”

提供“查看待审核事项”入口，而不是问“是否继续”。

## 4. 任务执行与审批状态模型

必须区分任务状态和审批状态，不能只用一个 `status` 字段表示全部状态。

### 4.1 任务状态

建议统一为：

- `queued`：等待执行。
- `running`：执行中。
- `waiting_approval`：等待人工决策。
- `blocked`：被未解决的依赖阻塞。
- `completed`：执行成功。
- `failed`：执行失败。
- `cancelled`：已取消。

如果多个子任务并行执行，父任务可以继续处于 `running`，同时存在一个或多个 `waiting_approval` 子任务。

只有真正无法继续的子任务才进入 `blocked`。

### 4.2 审批事项状态

建议统一为：

- `pending`：等待审核。
- `approved`：已批准。
- `rejected`：已拒绝。
- `deferred`：暂缓处理。
- `cancelled`：不再需要审核。
- `applying`：正在应用已批准的变更。
- `applied`：已成功应用。
- `apply_failed`：批准后应用失败。

`approved` 和 `applied` 必须是两个不同状态。

### 4.3 任务与审批之间的关系

一个任务可以产生多个审批事项；一个审批事项可以影响多个资产。

例如：

```text
Task: TASK-001
  ├── Subtask: Generate test cases / completed
  ├── Subtask: Analyze login requirement / waiting_approval
  ├── Subtask: Generate report / blocked by execution
  └── Approval: APR-001 / pending
```

审批事项应独立于 Agent 会话保存。

即使聊天窗口关闭、页面刷新或 Agent 会话结束，待审核事项也必须存在，能够重新打开并继续处理。

## 5. 审批触发规则与风险分级

采用基于风险的审批，而不是“每个阶段都需要确认”。

以下为第一版建议规则。

### 5.1 低风险：自动处理

典型操作：

- 需求文档格式整理。
- 测试点和用例标题规范化。
- 明确重复内容的去重建议。
- 非破坏性的草稿生成。
- 普通进度汇报。

处理规则：

- 在已授权范围内自动执行。
- 记录变更事件。
- 必要时提供抽样检查。
- 不要求用户逐项确认。

低风险自动修改也应保留可追溯记录。涉及共享基线的实际变更仍须遵守版本控制规则。

### 5.2 中风险：批量审核或抽样检查

典型操作：

- 合并相似测试点。
- 调整用例步骤或预期结果。
- 修改非核心资产的关联关系。
- 批量调整非关键用例的结构。

处理规则：

- 先生成变更提案。
- 同类事项支持批量审核。
- 用户可查看完整 Diff。
- 根据历史质量、任务类型和证据充分性决定是否抽样检查。

不能因为事项属于中风险，就默认允许 Agent 任意修改已经发布的基线。

### 5.3 高风险：必须逐项审核

典型操作：

- 将需求判定为删除。
- 废弃核心测试用例。
- 修改重要业务规则。
- 变更核心回归集。
- 无法确定新旧需求映射关系。
- 需要用户决定的业务歧义。
- 涉及破坏性测试数据操作。

处理规则：

- 必须创建审批事项。
- 展示证据和影响范围。
- 需要明确的人工决定。
- 不允许通过批量批准绕过高风险确认。

特别规则：新版本没有提及某条旧需求，不代表该需求已经删除。应标记为 `pending_review`，等待证据或人工决定。

### 5.4 高影响操作：需要明确授权

例如：

- 发布或替换正式 QA 基线。
- 在共享环境执行有破坏性的操作。
- 删除重要数据。
- 触发不可逆外部操作。

处理规则：

- 默认需要明确授权。
- 不得因选择“自主执行模式”就绕过危险操作的授权要求。
- 执行前再次校验权限、目标环境和参数。
- 对重要操作记录完整审计信息。

### 5.5 风险等级不能只由模型自行决定

风险评估至少结合：

- 操作类型。
- 影响范围。
- 可逆性。
- 资产重要性。
- 证据完整度。
- 任务授权范围。

模型可以提出风险判断，但关键的权限边界必须由确定性代码强制执行。

## 6. 工作模式配置

提供三种工作模式。

### 6.1 逐步引导模式

适用于首次使用、探索性任务或需要学习工作流程的用户。

- 每个主要阶段可以暂停。
- 用户可以检查阶段结果。
- 不应对每一条普通生成结果都弹出确认。
- 用户可以随时切换到其他模式。

### 6.2 智能协作模式（默认）

- Agent 自动推进满足前置条件的任务。
- 低风险事项自动处理。
- 中风险事项按策略批量审核或抽样检查。
- 高风险事项必须人工审核。
- 无关子任务可以继续运行。
- 阻塞原因和恢复条件明确可见。

### 6.3 自主执行模式

- 在明确授权的范围内连续执行。
- 结束后汇总成果、异常和失败。
- 仍然遵守强制审批规则。
- 不允许扩大任务权限。
- 不允许静默修改已发布基线或执行未经授权的破坏性操作。

模式配置应保存到项目或任务配置中，具体作用域根据现有配置体系决定。任务运行时应记录当时使用的策略快照，避免中途更改配置后无法解释任务行为。

## 7. 批量审批设计

### 7.1 支持批量处理的条件

多个事项满足以下条件时，可以放在同一个批次：

- 操作类型相同或兼容。
- 风险等级允许批量处理。
- 适用相同的审核策略。
- 不存在相互冲突的变更。
- 每条事项都有独立的审批结果。

例如，8 条用例只需要统一规范标题，可以提供：

- 全部接受。
- 全部拒绝。
- 逐项编辑。
- 仅接受选中项。

### 7.2 不允许无条件批量批准

下列事项不能因为出现在同一批次中而自动获得批准：

- 删除核心需求。
- 废弃核心用例。
- 修改重要业务逻辑。
- 发布正式基线。
- 执行危险操作。

用户选择“全部接受”时，系统必须排除需要逐项审核的高风险事项，并清楚显示仍待处理的数量。

### 7.3 幂等与并发保护

审批请求需要具备幂等性，避免重复点击造成重复应用。

应用变更前必须校验：

- 目标资产是否仍然存在。
- 资产当前修订是否与审核时一致。
- 目标版本是否已被其他操作修改。
- 相关依赖是否已经变化。

若存在冲突，不应静默覆盖，应将事项转入 `apply_failed` 或适当的冲突状态，并提供重新审核入口。

## 8. 版本演进与审批中心集成

审批中心必须支持需求版本、测试点版本、用例版本及其关联关系的演进。

### 8.1 基础模型

建议区分：

- `asset_id`：逻辑资产的稳定 ID。
- `revision_id`：资产具体修订的唯一 ID。
- `version_id`：项目版本或测试基线 ID。
- `changeset_id`：一组变更的唯一 ID。
- `approval_id`：审批事项 ID。

逻辑资产可以跨版本持续存在，但各版本中的具体内容必须可还原。

### 8.2 版本演进工作流

```text
导入新需求版本
    ↓
匹配旧需求与新需求
    ↓
生成版本 Diff
    ↓
分析影响的测试点、用例和脚本
    ↓
生成变更提案
    ↓
按风险自动处理或进入审批中心
    ↓
应用已批准的变更
    ↓
生成新版本资产快照
    ↓
验证核心回归集与资产追溯关系
```

需求变化可能对应以下类型：

- `unchanged`
- `modified`
- `added`
- `removed_candidate`
- `split`
- `merged`
- `pending_review`

测试资产迁移建议可以包含：

- `keep`
- `update`
- `create`
- `deprecate`
- `pending_review`

这些类型应以结构化字段保存，不要只依赖自然语言描述。

### 8.3 版本审批规则

- 不得因新版本缺少某项需求，就自动删除旧需求或测试用例。
- 每项迁移建议必须能查看新旧版本差异。
- 已批准的变更应用后生成新修订。
- 历史基线和执行记录不可被新版本覆盖。
- 基线发布前检查未解决的高风险审批事项。
- 对每次迁移保留审核人、理由、结果和影响范围。

### 8.4 回归集也要版本化

核心回归集应有独立的版本记录。

当需求变化影响核心回归场景时，Agent 可以提出新增、移除或调整建议，但核心场景的移除需要人工审核。

回归策略可以分为：

- Smoke Regression：快速冒烟验证。
- Core Regression：核心业务回归。
- Extended Regression：扩展回归。

执行层级不是用例生命周期状态，两者应独立管理。

## 9. 建议的领域数据结构

具体字段和 ORM 必须以现有仓库为准。以下为概念结构，不要求照搬成独立数据库表。

### 9.1 Task

```typescript
type TaskStatus =
  | "queued"
  | "running"
  | "waiting_approval"
  | "blocked"
  | "completed"
  | "failed"
  | "cancelled";

interface Task {
  id: string;
  projectId: string;
  sessionId?: string;
  parentTaskId?: string;
  title: string;
  status: TaskStatus;
  workMode: "guided" | "balanced" | "autonomous";
  policySnapshot: Record<string, unknown>;
  createdAt: string;
  updatedAt: string;
}
```

### 9.2 ApprovalItem

```typescript
type ApprovalStatus =
  | "pending"
  | "approved"
  | "rejected"
  | "deferred"
  | "cancelled"
  | "applying"
  | "applied"
  | "apply_failed";

type RiskLevel = "low" | "medium" | "high" | "critical";

interface ApprovalItem {
  id: string;
  projectId: string;
  taskId: string;
  title: string;
  description: string;

  category:
    | "requirement"
    | "test_point"
    | "test_case"
    | "automation"
    | "execution"
    | "regression"
    | "release"
    | "other";

  status: ApprovalStatus;
  riskLevel: RiskLevel;
  blocking: boolean;
  bulkEligible: boolean;

  targetAssetIds: string[];
  evidenceRefs: string[];
  beforeSnapshot?: unknown;
  proposedChanges?: unknown;
  rationale: string;
  impactSummary: string;

  requestedAction: string;
  decidedBy?: string;
  decision?: string;
  decisionReason?: string;

  createdAt: string;
  updatedAt: string;
}
```

注意：

- `bulkEligible` 不能仅由前端决定，服务端必须再次校验。
- `evidenceRefs` 应引用真实存在的文件、资产修订、事件或执行记录。
- 不要把整个大型需求文档复制进每条审批记录。
- `beforeSnapshot` 和 `proposedChanges` 应使用受控的版本化数据结构。
- 如果当前系统是单用户本地应用，也应保留操作来源和时间；多人审核字段可以在现有身份系统支持时扩展。

### 9.3 AuditEvent

记录审批中心的重要事件：

```typescript
interface AuditEvent {
  id: string;
  projectId: string;
  taskId?: string;
  approvalId?: string;
  eventType: string;
  actorType: "user" | "agent" | "system";
  actorId?: string;
  payload: Record<string, unknown>;
  createdAt: string;
}
```

事件示例：

- `task.started`
- `task.progressed`
- `approval.created`
- `approval.approved`
- `approval.rejected`
- `approval.deferred`
- `change.apply_started`
- `change.apply_succeeded`
- `change.apply_failed`
- `baseline.created`

审计事件应追加写入，不应通过修改旧事件来更新历史。

## 10. Agent Runtime 集成

### 10.1 不要把审批逻辑全部塞进 Prompt

Prompt 负责让 Agent 理解任务、生成分析和提出建议；任务调度、审批状态、权限校验和资产变更必须由确定性代码控制。

推荐的职责划分：

**Pi Runtime**

负责模型调用、工具执行、会话上下文和现有 Agent 能力。

**QA Core**

负责需求、测试点、用例、自动化、执行、缺陷和报告等 QA 领域逻辑。

**Task Orchestrator**

负责任务依赖、并行执行、任务状态、阻塞和恢复。

**Approval Service**

负责创建审批事项、权限验证、审批决策、批量审核和应用结果。

**Asset / Version Service**

负责资产身份、修订、版本快照、变更集、关系追溯和基线管理。

**QA Workspace UI**

负责进度展示、待审核列表、Diff、审核操作和执行结果展示。

这些是逻辑职责，不意味着必须新建六个独立服务。第一版优先复用现有模块，在代码边界清晰的前提下实现。

### 10.2 工具执行前的审批拦截

对于需要授权的操作，应在工具执行入口统一检查权限，而不是依赖模型自觉。

概念流程：

```text
Agent 请求执行工具
    ↓
解析操作类型和目标
    ↓
确定性权限校验
    ├── 允许自动执行 → 执行并记录事件
    ├── 需要人工审批 → 创建 ApprovalItem
    │                      ↓
    │                 等待用户决定
    │                      ↓
    │                 重新校验权限与数据
    │                      ↓
    │                 执行批准的操作
    └── 禁止操作 → 拒绝并返回原因
```

审批只授权特定操作、特定目标和特定参数范围，不应成为无限期的通用权限。

如果审批期间目标资产已经发生变化，必须重新审核，不得直接应用旧提案。

### 10.3 等待审批时的行为

- 不要让 Agent 无限轮询等待用户。
- 将任务和审批状态持久化。
- 释放不需要继续占用的执行资源。
- 用户作出决定后，通过任务调度器恢复相关任务。
- 不相关的任务可以继续执行。
- 页面关闭后，用户仍可重新打开待审核中心处理事项。

## 11. API 与事件设计

优先沿用现有项目的路由、RPC、事件机制和状态管理。以下仅为建议接口。

### 11.1 查询审批事项

`GET /api/approvals`

建议支持：

- `projectId`
- `taskId`
- `status`
- `riskLevel`
- `category`
- `page`
- `pageSize`

### 11.2 查看详情

`GET /api/approvals/:id`

返回审批详情、关联资产、证据引用、前后差异及可执行操作。

### 11.3 提交审核决定

`POST /api/approvals/:id/decision`

请求内容包括：

```json
{
  "decision": "approve",
  "reason": "已核对需求变更及影响范围"
}
```

服务端应：

1. 校验事项状态。
2. 校验用户权限。
3. 校验目标修订与基线是否发生变化。
4. 持久化审批决定。
5. 启动变更应用或任务恢复。
6. 记录审计事件。
7. 返回当前审批状态与执行状态。

不能在变更尚未成功应用时直接返回 `applied`。

### 11.4 批量审核

`POST /api/approvals/batch-decision`

要求：

- 每个事项单独校验。
- 高风险事项不允许通过普通批量批准绕过规则。
- 支持部分成功、部分失败。
- 返回每个事项的实际结果。
- 同一事项重复提交不产生重复变更。

### 11.5 任务操作

沿用现有任务机制实现必要操作：

- 查看任务详情。
- 查看任务子项与依赖。
- 暂停可暂停的任务。
- 取消任务。
- 恢复被审批阻塞的任务。
- 查看任务事件流。

不需要为了审批中心再建一套独立的会话系统。

## 12. 异常处理与恢复

必须处理以下场景：

1. 用户关闭页面，审批事项仍然保留。
2. 用户重复点击批准，不会重复应用变更。
3. 审批通过后应用失败，显示失败原因并允许安全重试。
4. Agent 执行失败，不应伪装成审批问题。
5. 某个子任务被阻塞，其他独立任务继续执行。
6. 审批期间资产发生变化，系统提示冲突并要求重新审核。
7. 用户拒绝建议后，Agent 根据拒绝原因决定是否重新生成方案；不得反复自动提交相同事项。
8. 用户暂缓事项后，系统记录原因并明确哪些任务受到影响。
9. 基线发布前仍存在未解决的强制审批事项，阻止发布。
10. 应用部分变更失败时，必须明确哪些变更成功、哪些失败，并提供恢复或继续处理方案。

对于涉及多个资产的批量应用，优先使用事务；若现有存储不支持跨资产事务，则采用可恢复的分批应用机制，并记录每项的执行状态。

## 13. 测试要求

### 13.1 单元测试

- 审批状态转换合法性。
- 风险等级与批量审批规则。
- 权限校验。
- 资产版本冲突检测。
- 幂等处理。
- 任务依赖和阻塞判断。
- 审批决策与审计事件生成。

- 创建任务后自动产生审批事项。
- 用户批准后任务正确恢复。
- 用户拒绝后相关任务按规则停止、重试或重新规划。
- 非阻塞事项不影响其他子任务。
- 批量审批支持部分成功。
- 页面刷新后状态一致。
- 应用失败后能够安全恢复。
- 版本演进过程中历史基线保持不变。

- 待审核数量与真实待处理事项一致。

- 审批通过与实际应用完成显示不同状态。

## 14. 验收标准

第一版至少满足以下条件：

- [ ] 现有 QA 流程可以连续执行，不再强制每阶段等待用户点击。
- [ ] Agent 能将需要人工决策的事项写入持久化审批列表。
- [ ] 页面刷新或重新打开后，审批事项仍然存在。
- [ ] 任务、审批、资产版本三个状态维度互相独立。
- [ ] 低风险操作可以在授权范围内自动执行。
- [ ] 中风险事项支持批量审核或抽样审核。
- [ ] 高风险事项必须逐项审核。
- [ ] 审批中心支持按项目、任务、风险、模块和状态筛选。
- [ ] 每个审批事项都能查看理由、证据和影响范围。
- [ ] 批量审核不会绕过强制审批规则。
- [ ] 审批通过不等于变更应用成功。
- [ ] 应用失败、重复点击和并发冲突均有明确处理。
- [ ] 一个子任务阻塞不会无条件阻塞整条 QA 流水线。
- [ ] 需求、测试点、用例和脚本的历史修订可追溯。
- [ ] 历史执行记录绑定具体资产修订和版本基线。
- [ ] 基线发布前可以检查未解决的强制审批事项。
- [ ] 原有 Pi Web 开发模式和 QA 工作台继续可用。

## 15. 实施计划

### Phase 0：现有代码审计

先检查仓库，输出简短的架构分析：

- 现有 Pi Web 入口、路由和页面组件。
- Pi Runtime 的调用与工具执行入口。
- 当前 QA 工作流、阶段状态及持久化方式。
- 现有 QA 资产与版本数据结构。
- 当前事件流和 UI 状态管理方式。
- 可以复用的组件与需要调整的模块。

先确认事实，不要假定项目已经有完整的 Task、Approval 或 Version Service。

### Phase 1：审批中心最小闭环

实现：

- 审批事项数据模型与持久化。
- 审批列表与详情页面。
- 批准、拒绝、暂缓。
- 审批状态与审计事件。
- 与现有 Agent 工作流连接。
- 页面刷新后恢复审批状态。

验收：Agent 可以创建待审核事项，用户可以在统一入口处理，处理结果能回写任务。

### Phase 2：风险策略与自动推进

实现：

- 三种工作模式。
- 风险等级与操作权限策略。
- 自动推进符合条件的子任务。
- 局部阻塞。
- 批量审批。
- 幂等与失败恢复。

验收：常规工作不再逐阶段等待用户确认，高风险事项仍受控。

### Phase 3：版本演进集成

实现：

- 版本与资产修订模型。
- 需求与测试资产 Diff。
- 变更提案与审批事项关联。
- 审批后生成新修订。
- 历史基线与执行记录保护。
- 核心回归集版本化。

验收：旧版本资产可以还原，新版本的迁移建议可审核、可追溯，未经批准的高风险变更不会被直接应用。

### Phase 4：体验与质量优化

实现：

- 审批耗时、驳回率和返工率统计。
- 低风险事项抽样检查策略。
- 常见审核操作优化。
- 失败恢复与审计体验完善。

这些指标用于评估审批机制是否真正降低人工负担，不应为了减少点击次数而降低质量门槛。

## 16. 给 Cursor 的开发约束

开始编码前，必须遵守以下要求：

1. 先阅读仓库中的架构、现有 QA 工作流、Pi Runtime 接入方式和数据持久化方案。
2. 先输出实际代码结构与本规格之间的映射，再提出实现计划。
3. 复用已有组件、状态管理、路由和工具执行机制；不要未经分析就重写。
4. 保留 Pi Runtime，将 QA 领域逻辑放在清晰的 QA Core 边界内。
5. 不要把整个功能实现成 Prompt 中的一段自然语言规则。
6. 不要只做静态审批页面；必须连接真实任务、真实审批状态和真实执行结果。
7. 不要一次性大规模重构所有 QA 模块。
8. 每个阶段都要有对应测试。
9. 若发现当前架构无法支持某项要求，先说明原因、风险和最小改造方案，不要自行删除产品要求。
10. 第一版不要求完整复刻 Git 的分支系统，也不要求引入 Neo4j 或重型 RAG。
11. 版本差异、审批状态、权限校验和变更应用应由确定性代码负责；AI 主要负责分析、生成建议和解释证据。
12. 所有 UI 文案以测试人员容易理解为准，避免把内部 Agent 技术概念直接暴露给用户。

## 17. 最终产品定义

OpenTest 不应该要求测试人员不断监督 Agent 的每一步。

它应该让用户：

- 明确告诉 Agent 要完成什么任务。
- 在必要时查看 Agent 正在做什么。
- 集中处理真正需要判断的问题。
- 查看每个建议背后的证据。
- 对高风险操作保留最终决定权。
- 在完成后获得可追溯、可复现的 QA 资产和结果。

**最终原则：流程自动推进，决策集中处理，风险明确升级，资产版本可追溯。**
