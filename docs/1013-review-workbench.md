# 待审核工作台

测试人员负责判断质量、处理风险和做关键决定。Agent 负责把常规生成做完。人不再在每个模块结束后按一次「继续」。

这份设计收束两份材料：`docs/1012-human-limit-update.md` 里的审批中心，以及「自动流水线，异常才停车」的分工。它落在现有 Pi Web 工作台上，不另建任务服务、审批服务或版本服务。

页面上的「测试模式 / 开发模式」保持不变。本文的三种策略是测试模式里的任务策略，管的是 QA 流水线停不停，不管能不能改产品代码。

## 1. 两条线

流程条回答「做到哪了」。待审核回答「有什么要人判断」。

| | 阶段推进 | 内容审核 |
|---|---|---|
| 问的问题 | 前置条件够不够，可以写下一步吗 | 这段内容能不能当真 |
| 放在哪 | 左侧流程条、总览 | 待审核 |
| 谁决定 | 代码看规则 | 人看证据 |
| 典型动作 | 这一节图谱写完了，继续下一节 | 这条规则互相矛盾，先不要写成用例 |

聊天区报告进度、解释证据、回写决定。普通进度不要求回复。需要决定的事项必须在待审核里打得开，不能只存在某一句对话里。

总览上每个阶段增加一种可见状态：进行中，同时有待审事项。阶段可以继续写文件，待审事项另算。

## 2. 任务策略

开始处理一份文档时确认一次：文档、可选的基线文档、任务策略。默认是智能协作。策略写在产品目录 `tasks/policy.json`，并在当次任务里留一份快照，避免做到一半改了策略却说不清当时为什么停。

**逐步引导。** 适合第一次走通。每个主要阶段写完可以看一眼。不要对每一条草稿都弹确认。分析仍按节写图谱，但同一节里的多条待澄清进队列，不每条都停一次对话。

**智能协作（默认）。** 常规生成连续做完。低风险自动记下。中风险进队列，可以批量处理或抽样。高风险必须逐项看。一个功能被挡住时，不依赖它的功能继续写。

**自主执行。** 在本次授权范围内连续做完，结束时交一份汇总：完成了什么、哪些进了待审核、哪些失败了。高风险和下面的 L4 仍然要人决定。选了自主执行也不能删除核心用例、发布基线或改共享环境。

三种策略共用同一套风险级别。差别只在 L1、L2 要不要等人点。L3、L4 在三种策略里都要人决定。

## 3. 风险级别

级别由操作类型、影响面、能不能撤销、证据够不够决定。模型可以建议级别，不能把下面表里的 L3、L4 降成自动执行。置信度高也不等于可以自动删。

| 级别 | 在本系统里的操作 | 智能协作怎么处理 |
|---|---|---|
| L0 常规生成 | 读文档、按节追加图谱、写测试点草稿、写用例草稿、进度汇报 | 自动做。图谱已存在时禁止用替换模式重写整张图 |
| L1 低风险修改 | 标题和格式整理、明确的重复项合并建议、非破坏性的草稿补全 | 自动改，并在审计里留一条。不改已确认用例的步骤和期望 |
| L2 需要判断 | 测试点是否覆盖对了、用例步骤和期望是否合理、非核心关联调整、选择器自愈后留哪一版 | 先生成或先执行，再进入待审核。同类可以批量接受。不挡住其他功能 |
| L3 高风险 | 把旧功能当成删除或下线、废弃核心用例、规则互相矛盾、业务规则缺失、改核心回归范围、新旧对不上 | 逐项审核，不能被「全部接受」带走。只挡住依赖它的功能 |
| L4 高影响 | 把演进方案应用成新基线、在共享环境执行、删除重要数据、打开沙箱录制 | 单独授权。授权只针对这一次操作、这一个目标 |

和现有产物的对应：

- 需求知识里的「待处理」按内容分派。缺规则、互相矛盾、疑似删除，是 L3。其余歧义是 L2。忽略、已补充、待讨论一旦标好，就离开队列。
- 测试点的「待确认」是 L2。生成本身是 L0。
- 版本演进里「新版未提及」「下线」「处置互相矛盾」是 L3。保留并回归是 L2 或更低，应用进基线仍是 L4。
- 选择器自愈保持现在的做法：先换上新选择器把这次跑完，前后两版都留着。留哪一版是 L2，不在跑之前停下来问。
- 录制必须人在沙箱里操作，属于 L4，不因为策略是自主执行就自己打开浏览器去点。

待讨论、忽略、已补充的含义不变：忽略的不要再写进测试；已补充以补充为准；待讨论的不要编造结论，依赖它的用例先不写。

## 4. 智能协作时流水线怎么走

用户确认任务范围之后，Agent 连续做这些事，中间不问「要不要继续」：

1. 按节读文档，追加图谱，把新的待澄清写进 `knowledge/需求评审.md`。
2. 按功能写测试点，状态仍是待确认。
3. 对没有 L3 阻塞的功能写用例草稿。用例的自动化仍写否。
4. 若同时给了基线文档和改版文档，先出版本演进方案，不改旧用例，不覆盖图谱。
5. 停在待审核。聊天里只汇报：完成了哪些模块，有几项高风险，几项可以批量看。

结构不合格不算「可以继续」。测试点缺编号、优先级或状态，用例缺步骤或期望，这一份文件先补全，不进入下一功能。这是生成失败，不是审批。

一个功能有未解决的 L3 时：

- 这个功能的用例、脚本先不写。
- 进度里这一格标成等待决定，不标成失败。
- 其他功能继续。
- 人处理完之后，从被挡住的这一格接着写，不重做已经写完的功能。

现有进度文件继续用 `tasks/checkpoint.json`。步骤完成表示文件已经写好，不表示内容已经接受。待审核另算，避免一个状态字段同时表示「写完了」和「人还没看」。

## 5. 待审核工作台

在现有工作台导航末尾增加「待审核」。数量只统计还没决定的事项。高风险另计一个数。进度通知不进这个数。

列表按风险分成三组，不按阶段拆成七个待办箱：

- 必须逐项看：L3、L4。
- 建议抽样：L2 里证据弱或改了步骤、期望的。
- 可以批量处理：同一类 L2，例如这一批测试点都是待确认。

每一行有标题、所属功能、风险、一句原因、关联了几条资产、会不会挡住后续、建议动作。

点开之后在同一页看完，不把人送回聊天里翻上下文：

- 为什么要人判断。
- 依据：需求里的原句、图谱场景、或演进方案里的对照。长文档只引用位置，不把全文抄进待办。
- 改之前和改之后。没有改动的草稿写明「这是新生成的，还没有旧版本」。
- 影响：哪些测试点、用例、脚本依赖它。
- 动作。

动作跟来源走，不发明第四套按钮：

| 来源 | 动作 |
|---|---|
| 需求知识 | 忽略、已补充、待讨论。已补充必须写上补充 |
| 测试点 | 确认、退回。退回写一句哪里不对 |
| 用例草稿 | 接受、退回 |
| 版本演进 | 保留、需更新、废弃、暂缓、生成候选、不采纳。高风险的废弃和「当成删除」不能进全部接受 |
| 自愈 | 留下新选择器、回到旧选择器 |
| 应用基线 | 单独的「应用已选」。点了之后如果文件在审核期间被改过，应用失败并说明原因，不显示成已完成 |

「全部接受」只作用于当前筛选里允许批量的行。点下去之前写明：将接受多少项，排除多少项高风险。排除的项留在列表里。

决定写回原来的文件：需求评审、测试点、用例、演进方案、自愈记录。待审核面板是这些文件的同一队列，不另存一份会过期的副本。页面刷新后队列还在，因为文件还在产品目录里。

批准和应用分开的，只有会改已有基线的操作。版本演进保持现在的两步：先选定，再「应用已选」。应用失败保持方案为未应用，并写明哪几条没写上。测试点和待澄清的标记本身就是决定，点下去就是写回那一行，不再套一层「应用中」。

同一事项重复点击不重复改。目标文件的指纹和打开详情时不一致，就拒绝这次写入，让人重新看。

## 6. 总览和聊天

总览保留七段进度：需求、测试点、用例、录制、执行、缺陷、报告。每段除了未开始、进行中、有失败、已完成，还能显示「有待审」。有待审不把整段算作失败，也不挡住其他段。

「让 Agent 做这一步」在智能协作里改成开始整批任务，而不是只做当前这一格然后停住。逐步引导才保留「做完这一阶段先停」。

聊天里的结束语改成结果汇总，例如：8 个功能的测试点和用例草稿已经写好；2 项要逐项看，4 项可以一起看。附带打开待审核。不要问要不要继续。

人在待审核里做出决定后，聊天里追加一条短记录：谁在什么时间对哪一条做了什么。记录追加，不改旧记录。

## 7. 第一版做这些，不做那些

做：

- `tasks/policy.json` 和总览上的策略选择。默认智能协作。
- 待审核面板，读现有的需求评审、测试点、用例、演进方案、自愈记录。
- 技能和 `STAGE_REQUESTS` 里「写完一个功能就停下等确认」的句子，在智能协作下改成连续做完，只把 L3、L4 放进队列。
- 代码里写死 L3、L4 名单。模型不能把「下线」「新版未提及」「废弃核心用例」「应用基线」标成自动执行。
- 一个功能遇到 L3 时跳过它的用例，继续下一个功能。
- 全部接受时排除 L3、L4。
- 演进应用继续比对文件指纹。

不做：

- 父子任务并行、多会话同时跑。
- 资产修订号、回归集的独立版本。
- 每一次写文件都先弹授权。
- 为了少点击而自动废弃用例或覆盖旧图谱。
- 审批耗时和驳回率的统计页。第一版只在 `knowledge/evolution/audit.jsonl` 同一类追加日志里记下决定，供以后对比逐步引导和智能协作。

## 8. 怎样算做成

- 智能协作下，8 个功能的测试点可以一次写完，对话里不再出现 8 次「要继续吗」。
- 待审核里的数量等于还没决定的事项，刷新后还在。
- 一条待讨论或疑似删除只挡住依赖它的功能，其他功能的草稿已经在目录里。
- 全部接受不会把下线、废弃核心用例、应用基线一起带走。
- 演进方案在人点应用之前，不改旧用例，不覆盖 `graph/graph.json`。
- 图谱里已经有内容时，后续分析只用追加。
- 测试模式、开发模式和现有文件浏览仍可用。

## 9. 审核经验：同类的事交给 Agent

人在待审核里做的决定，系统自动记成经验。不要每条都再点一次「记成经验」。

循环是这样的：

1. 人对一条待澄清写了补充或忽略，或者带着理由退回测试点、用例。系统立刻写入经验文件。文档写法（删除线、划掉、以截图为准、正文未含、不用测试）记到 `~/.pi/agent/opentest/审核经验.md`，编号 G001，所有产品都能用，并且会马上套到当前产品里还没处理的相似条目。项目逻辑记到本产品 `knowledge/审核经验.md`，编号 R001，只在这个产品生效，不自动套到其他待处理项。
2. 同一条经验再次出现时只增加命中次数，不新开一条。关键词对不上的才另记。
3. 待处理的待澄清里，关键词全部出现的条目归到「符合已有经验」。全局经验会自动处理；本产品经验可以一键「按 R001 处理 N 条」。涉及下线、删除、矛盾、缺失规则的仍留在「必须逐项看」。
4. Agent 写新的待澄清时读两份经验文件。相符且不是高风险的，直接写成经验的决定和做法，并带 `- 依据：审核经验 R001`。这些条目进「Agent 按经验处理（抽查）」，可以认可、推翻。推翻两次自动停用。
5. `tasks/review-log.jsonl` 每满 100 条，系统合并经验文件：相同关键词和决定的条目合成一条，停用的搬进 `审核经验.归档.md`，本产品里和全局重复的并入全局。人可以随时打开「审核经验」面板查看、改做法、改范围、停用，也可以直接改那两份 markdown。
6. Agent 发现审核记录里同类决定出现两次以上、还没有经验时，可以追加一条状态为待确认的候选经验。候选只能由人启用。

经验不会让 L3、L4 自动执行。
