# OpenTest Specification

**Version:** 0.2
**Status:** Development Specification
**Product:** OpenTest
**Type:** AI-native QA Agent / QA Operating System

---

# 1. 产品定义

OpenTest 是一个 **AI-native QA Agent**。

它不是：

* AI 自动点网页
* AI 用例生成器
* Playwright Recorder
* 测试管理系统
* 一个简单的 Chatbot

而是：

> **一个能够理解需求、建立测试知识、设计测试、执行测试、分析结果、管理缺陷，并持续维护自动化资产的完整 QA Agent。**

核心目标：

```text
Requirement
    ↓
Understand
    ↓
Test Knowledge
    ↓
Test Strategy
    ↓
Test Points
    ↓
Test Cases
    ↓
Automation
    ↓
Execution
    ↓
Diagnosis
    ↓
Defect
    ↓
Report
    ↓
Knowledge Update
```

最终形成：

```text
需求 → 测试 → 执行 → 反馈 → 知识 → 下一轮测试
                    ↑______________↓
```

# 2. 核心设计原则

## 2.1 Agent First, Automation First

Agent 负责：

```text
理解
推理
生成
分析
决策
修复
```

确定性程序负责：

```text
存储
执行
校验
调度
报告
```

原则：

> **能确定执行的事情，不交给 LLM。**

---

# 2.2 Human-in-the-loop，而不是 Human-as-operator

人不应该成为 Agent 的鼠标。

错误：

```text
Agent：
“请告诉我下一步点击什么”
```

正确：

```text
Agent：
“我分析出 27 个测试点，其中 3 个存在需求歧义。”

Human：
确认 / 修改

Agent：
继续执行。
```

人只在：

```text
高价值决策
高风险操作
需求歧义
测试结论
缺陷确认
```

出现。

---

# 2.3 Evidence First

OpenTest **永远不能凭 LLM 判断生成测试结果。**

所有测试结论必须来自：

```text
Browser
API
Console
Network
Database
Logs
Screenshots
Trace
Execution Result
```

LLM 只能：

```text
interpret evidence
```

不能：

```text
invent evidence
```

例如：

错误：

```text
测试通过，因为 Agent 判断页面应该没问题。
```

正确：

```text
PASS

Evidence:
HTTP 200
Response body matched expected schema
UI element visible
Screenshot captured
```

---

# 2.4 Deterministic First → Agent Fallback

正常执行：

```text
Test Case
 ↓
Deterministic Executor
 ↓
Result
```

只有异常：

```text
Failure
 ↓
Diagnostics
 ↓
Agent
 ↓
Repair / Diagnosis
```

不要：

```text
每一步都：
Observe → LLM → Action → Observe → LLM
```

这是 OpenTest 与纯 Computer-use Agent 的核心区别。

---

# 2.5 Learn Once, Reuse Many

Agent 做一次重工作：

```text
Requirement Analysis
Test Design
Automation Generation
```

之后：

```text
100 次执行
```

应该尽量：

```text
0 LLM
```

而不是：

```text
100 × N LLM calls
```

# 7. 交互原则

## 7.1 一个问题只问一个决策

不要：

```text
请输入：
URL、浏览器、账号、密码、环境、模式……
```

应该：

```text
需要录制自动化测试。

选择环境：

❯ 测试环境
  预发布环境
  自定义 URL
```

然后：

```text
测试环境 URL：

https://test.example.com
```

---

# 7.2 所有选择提供默认值

例如：

```text
模型：

❯ DeepSeek
  OpenRouter
  Ollama
  Custom
```

Enter 即可。

原则：

> **90% 的用户按 Enter 就能继续。**

---

# 7.3 永远告诉用户“现在发生了什么”

不要：

```text
Thinking...
```

应该：

```text
◐ 正在分析需求
  已读取 18,432 tokens

✓ 提取 23 条业务规则
✓ 识别 8 个业务模块
✓ 发现 4 个需求歧义

下一步：生成测试点
```

---

# 7.4 长任务必须可中断

任何阶段：

```text
Ctrl+C
```

不能意味着工作丢失。

必须：

```text
Checkpoint
```

保存状态。

再次启动：

```text
发现上次未完成的任务：

筑安通
进度：Test Cases 52 / Automation 31

❯ 继续
  从头开始
  查看进度
```

# 12. Requirement Graph

Graph 是：

> **测试知识的索引，不是整个系统的数据库。**

MVP：

```text
Primary Storage:
SQLite / JSON

Optional:
Neo4j
```

Neo4j 只是增强查询能力。

不能让：

```text
Neo4j unavailable
```

导致：

```text
OpenTest unavailable
```

当前仓库已经具备 Neo4j unavailable 时写入 `graph/` 的 fallback，这个方向应该保留。

# 14. Test Point

Test Point 是：

> 一个可以独立验证的行为。

例如：

```text
TP-001

项目名称为空时不能创建项目

Priority: P0

Precondition:
用户已登录

Expected:
系统阻止提交
显示“项目名称不能为空”
```

---

# 15. Test Case

Test Case 是：

> 可以执行的完整测试流程。

例如：

```text
TC-001 创建项目

前置条件：
管理员已登录

步骤：
1. 进入项目管理
2. 点击创建项目
3. 输入项目名称
4. 选择地区
5. 点击提交

预期：
项目创建成功
项目出现在列表中
```

Test Point ≠ Test Case。

---

# 16. Coverage Engine

OpenTest 必须知道：

```text
需求覆盖了多少？
测试点覆盖多少？
自动化覆盖多少？
执行覆盖多少？
```

例如：

```text
Requirements        42
Test Points         87
Test Cases          104
Automated           71
Executed            71

Requirement Coverage    95%
Test Automation         68%
Execution Coverage      100%
```

不要只给：

```text
52 tests passed
```


# 21. Execution Engine

Execution Engine 不负责“思考”。

它负责：

```text
Run
Timeout
Retry
Collect Evidence
Cleanup
Result
```

执行器：

```text
Browser Executor
API Executor
Shell Executor
Future:
DB Executor
Performance Executor
Mobile Executor
```

统一接口：

```typescript
interface Executor {
  prepare(): Promise<void>
  execute(test: TestCase): Promise<Result>
  cleanup(): Promise<void>
}
```

# 24. Repair Agent

只有：

```text
Locator Failure
Test Maintenance
Environment Change
```

适合自动修复。

例如：

```text
Old:

```

```text

reason
evidence
confidence
```

# 25. Repair Policy

不能让 Agent 无限制修改测试。

必须：

```text

 ↓
Validation
 ↓
Replay
 ↓
Evidence
 ↓
Accept / Reject
```

只有重新通过：

```text
Repair Candidate
```

才可以进入候选版本。

# 30. Model Routing

不同 QA 任务使用不同模型。

```text
Requirement Analysis
→ Strong Model

Test Design
→ Strong / Medium

Test Case Generation
→ Cheap Structured Model

Report
→ Cheap Model

Failure Diagnosis
→ Strong Model

Selector Repair
→ Cheap / Medium
```

配置：

```json
{
  "task_models": {
    "requirementAnalysis": "strong",
    "testDesign": "strong",
    "testCaseGeneration": "cheap",
    "failureDiagnosis": "strong",
    "repair": "cheap",
    "report": "cheap"
  }
}
```

当前仓库已经支持 task-level model routing，这应该升级为核心架构，而不是辅助功能。

# 34. Tool Safety

所有高风险 Tool 必须有权限级别：

```text
READ
WRITE
EXECUTE
DESTRUCTIVE
```

例如：

```text
read_requirement
READ

create_test_case
WRITE

run_test
EXECUTE

delete_test_data
DESTRUCTIVE
```

Agent 默认：

```text
READ allowed
WRITE confirmation when needed
EXECUTE confirmation according to project policy
DESTRUCTIVE always confirm
```

# 35. Human Gates

不要把所有东西都停下来问用户。

只保留真正有价值的 Gate。

## Gate 1 — Test Design

```text
发现 37 个测试点。

其中：
P0: 12
P1: 17
P2: 8

发现 2 个需求歧义。

[查看测试点]
[确认并继续]
[修改]
```

---

## Gate 2 — Destructive Action

例如：

```text
即将执行：

删除 12 个测试数据

环境：
测试环境

[继续]
[取消]
```

---

## Gate 3 — Release / Final Conclusion

OpenTest 不应该自动做：

```text
Release Sign-off
```

最终：

```text
测试结论建议：
风险：High

请 QA / PM / Tech Lead 决策。
```

你当前 README 中已经明确禁止自动 release sign-off，这个原则应该保留。


```text
        │                 │

   │    │    │       │    │    │

   │    │
   └────┴──────┐
               ↓
          Test Strategy
               ↓
          Test Cases
               ↓
           Execution
               ↓
          Diagnosis
               ↓
            Defect
               ↓
            Report
               ↓
         Knowledge Loop
```

最终目标：

> **OpenTest 不是帮 QA 写几个测试用例，而是让一个 QA Agent 接管从“理解需求”到“测试结论”的整个工作流。**

# 53. 最重要的架构判断

未来无论加：

```text
Performance Test
Security Test
Mobile Test
API Test
Database Test
Compatibility Test
Accessibility Test
```

都不要修改上层 QA Workflow。

只扩展：

```text
Executor
```

例如：

```text
Test Case
   ↓
Execution Planner
   ↓
┌──────────────┬─────────────┬──────────────┐
│ Browser      │ API         │ Performance  │
│ Executor     │ Executor    │ Executor     │
└──────────────┴─────────────┴──────────────┘
```

因此：

> **QA Workflow 是稳定层，Executor 是扩展层，Agent 是智能层。**

这是整个 OpenTest 最关键的架构边界。
